# Engineering methodology

TIQACC is built with a thin governance layer around a spec-driven, test-first increment workflow.
The approved design and its rationale are in
`docs/sources/SRC-005-framework-review/framework-review-2026-10-20.md` (DEC-0001); this file states
the rules that tools, agents and people follow. Where the two differ, record a dispute and ask the
governance owner.

## Lifecycle

| Phase | Purpose | Ends with |
| --- | --- | --- |
| L0 Framework | Set up this governance framework (F0) | Gate 0 |
| L1 Discovery | Clause index of SRC-001, business objectives, actors, bracketed-value workbook, missing annexure inputs, release-1 scope proposal | (continues into L2) |
| L2 Requirements assurance | Independent challenge of L1 output; re-verification of claims in SRC-002 and SRC-003 | Gate A |
| L3 Architecture and design | Architecture decisions (including the stack ADR) and detailed design for release 1 | Gate B |
| L4 UX and test specification | Prototypes and executable acceptance specifications, per increment | Gate C (per increment) |
| L5 Build | Test-first implementation of small, reviewed work items | (per work item) |
| L6 Release readiness | Release evidence; internal release approval | Gate D |
| L7 Improvement | Retrospectives; pruning or strengthening of the framework | (continuous) |

## Gates

| Gate | Entry evidence | Approved by |
| --- | --- | --- |
| Gate 0 | F0 acceptance tests passed; validation report; framework decisions recorded | Governance owner |
| Gate A | Release-1 requirements Approved; every release-1 requirement traces to a clause or a decision; assurance findings dispositioned; open questions classified as blocking or not | Human PO, with the qualified accountant for accounting policy |
| Gate B | ADRs including the stack ADR; detailed design for release 1; risks accepted or resolved | Tech lead (security owner for exceptions) |
| Gate C | Ready-for-implementation conditions met for every story in the increment (`trace readiness`); every acceptance criterion has a test ID | Human PO and tech lead |
| Gate D | Release manifest at one commit; E2 evidence; no open Critical or High defect unless waived; reviews complete | Release authority and PO (accountant for Tier-1 scope; security owner for security exceptions) |

Customer module acceptance under SRC-001 §2.16.4 is separate from Gate D and has no exception route:
per-module acceptance tests run by the customer's users with evidence, no open critical or high
defect, and one full accounting cycle run in parallel with differences explained in writing. Each
migration load is reconciled and signed by Finance (§2.16.2).

Gate records live in `docs/governance/gates/`. A gate passes only when its decision record is captured
(Stage 0 hook or git host) against the gate record's current hash.

## Risk tiers

| Tier | Scope | Before merge | Before release |
| --- | --- | --- | --- |
| Tier 1 | Posting, numbering, periods, audit, authorisation, isolation, money and rounding, financial data migration | E2 tests for every acceptance criterion and scenario; agent review; human review (E1); accountant sign-off where policy is touched | Operational verification in a test environment |
| Tier 2 | Module logic, APIs, integrations | E2 tests for every acceptance criterion; agent review; human review | E2 regression run |
| Tier 3 | Presentation, documentation, tooling | E2 or E3 tests; agent review; human approval may cover a batch | E2 regression run |

## Evidence levels

| Level | Source | Can establish |
| --- | --- | --- |
| E1 | A person's decision on an authenticated account no agent holds (git host, single sign-on) | Approvals, risk acceptances, human review |
| E1-op | Operator-attested: an exact approval phrase typed in the Claude Code session, captured by the UserPromptSubmit hook | Stage 0 approvals; never Tier 1; re-confirmed at Stage 1 |
| E2 | Generated by CI: run ID, commit, stored artifacts | Built, tested, scanned, deployed |
| E3 | Captured locally by `tools/governance/run_tests.py` or a hook: command, exit code, tree hash, clean flag | Supporting evidence; never release-grade |
| E4 | An agent's statement, including an agent's review | Nothing on its own |

## Status model

Artifacts store one authoring status: Draft, In review, Proposed, Approved, Rejected, Deferred,
Superseded. Approved is accepted by `check` only with a valid, unrevoked decision record on the
artifact's current normative hash.

Derived states are computed by `trace`, never stored: Specified, Implementation claimed, Implemented,
Tested, Agent-reviewed, Reviewed, Deployed, Operationally verified. Each is evaluated at a named
commit (and environment where relevant); evidence from another commit is stale. Approvals bind to
content hashes instead of commits.

Vocabulary: **void** (approval hash no longer matches), **at risk** (an upstream dependency changed),
**stale** (evidence from another commit), **disputed** (agent claim contradicted by tool evidence),
**pending** (awaiting a named person's decision).

## Change control

After Gate A, a normative change to an Approved artifact goes through a change request (CR): impact
analysis (`trace impact`, owners per dimension), a decision by the authority named for that kind of
change, a new artifact version, re-approval, and revalidation. Behaviour that violates an approved
requirement is an implementation defect unless an approved change request says otherwise.

## Disputes and escalation

When findings conflict, the orchestrator opens a dispute record with each side's evidence. Factual
disputes are settled by evidence or tests; policy disputes go to the owner in the authority matrix.
No majority votes, and never "first proposal wins".

## Break-glass

An emergency change needs a named approver and an emergency change request. Its records are flagged,
and the retrospective review, tests and approvals are completed within 5 working days.

## Overhead budget

Each increment reports the framework's cost: elapsed time from draft to decision, tokens per story,
the share of review findings acted on, and the time people spend reviewing. Controls that cost more
than they catch are candidates for pruning in L7.
