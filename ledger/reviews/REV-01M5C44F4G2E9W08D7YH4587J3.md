## F1 (high) - quoted or escaped options passed the agent deny list: CLOSED

The fix feeds each deny pattern two spellings of the command: the text as written (slashes
normalised) and `bare`, the command with quote and escape characters (`" ' ` + backtick + backslash`)
removed, so an option re-assembles after the shell strips its quoting
(`.claude/hooks/guard.py:272-275`, using UNQUOTE at `:45`). Checked against every probe in the brief:

- `git log -1 "--output=x"`, `'--output=x'`, `--out"put"=x`, `--out''put=x` -> `bare` becomes
  `... --output=x`, which matches `\s--output(=|\s|$)` -> blocked (guard.py:272-275;
  agent-scopes.json:42). Confirmed by test_quoted_or_escaped_options_blocked_for_agents.
- `--outpu\t=x` -> UNQUOTE strips the backslash, giving `--output=x` -> blocked (same path).
- `$'--output=x'` and `{--output=x,}` -> the "$" and the braces are rejected first by
  AGENT_FORBIDDEN (guard.py:49,265-269).
- `find . "-delete"`, `find . "-exec" echo x` -> `bare` is `find . -delete` / `find . -exec ...` ->
  matches `\s-(exec|...|delete)(\s|$)` -> blocked (agent-scopes.json:47). `rg "--pre=cat" x` ->
  `bare` is `rg --pre=cat x` -> matches `\s--pre(=|\s|$)` -> blocked (agent-scopes.json:45).

The orchestrator side of F1 is closed the same way: deny patterns now run against both the
slash-substituted text and the quote-stripped `bare` spelling (guard.py:288-291), so `git "push"`,
`git 'push' origin main` and `git p"ush"` are blocked (test_orchestrator_quoted_push_blocked). And
next to a protected path _read_only now requires a match on both spellings (guard.py:185-187), so
`git log -1 "--output=ledger/approval-decisions/APR-X.json"` and `find <SRC dir> "-delete"` are
blocked because the quote-stripped spelling trips the READ_ONLY negative lookahead that the quoted
spelling evaded (test_orchestrator_quoted_options_next_to_protected_paths_blocked).

Beyond the enumerated probes, I checked that the deny list is backed by a tight allow-list, not the
other way round: an agent's command must match a profile allow pattern on its first word
(agent-scopes.json:50-62), so program-executing options reachable only via `git -c core.pager=...`,
an inline `ENV=val git ...`, `--exec-path`, or a full-path command name like `/bin/sh` never pass,
because the subcommand/command must be the first token (the allow regex is anchored with `^`). That
closes the general case behind F1, not only the six probes.

## Q2 - agents could read anything the OS account can read: CLOSED for the listed vectors

Two complementary controls were added:

1. Shell: every path token an agent names must resolve inside the repository
   (_outside_repository, guard.py:165-182, called at :280-282). `cat ~/...` is caught by the tilde
   clause of AGENT_FORBIDDEN (`(?:^|[\s=:])~`, guard.py:49); `cat ../notes.txt`,
   `head docs/../../notes.txt`, `git diff --no-index <outside> CLAUDE.md` and `ls //server/share`
   are caught because the escaping token resolves outside (or starts with `//`). Confirmed by
   test_agent_shell_paths_must_be_inside_repository, which also asserts the normal-work commands
   (`git log A..B -- docs`, `git show HEAD~1:CLAUDE.md`, `rg -n "^def " tools`,
   `cat docs/governance/x.md`) remain allowed.
2. Tools: Read, Grep and Glob are added to the hook matcher (settings.json:82) and routed to
   _decide_read (guard.py:330-331), which blocks a candidate path that resolves outside the
   repository or is a network path (guard.py:241-258). Confirmed by
   test_agents_read_only_inside_repository, including the UNC form and a tempdir `path`, and that
   the orchestrator (no agent_type) is unaffected.

I verified the tilde anchoring does not over-block a git revision: `HEAD~1` keeps its "~" because the
preceding char is a letter, not start/space/"="/":" (so `git show HEAD~1:CLAUDE.md` is allowed while
`cat ~/x` is blocked). The residual read gaps I could construct are the Glob/Grep remainder and the
glued-option token (non-blocking findings 1 and 2 above); neither defeats the listed Q2 vectors, but
finding 1 is the one I would most like a live probe to settle.

## RISK-003 residuals left to the commit-time checks - I agree

The brief asks whether I disagree with leaving three items to the commit-time checks: a recursive
command on a folder that contains protected paths (`find docs/sources -delete`), paths assembled in
shell variables, and full-path command names. I agree, with one clarification that matters:

- For AGENTS these three are already closed by this commit, not merely deferred. `find docs/sources
  -delete` trips the `-delete` deny pattern; any "$" (variable assembly) trips AGENT_FORBIDDEN; and a
  full-path command name like `/bin/rm` fails the anchored allow-list and also resolves outside the
  repository. So the residual is ORCHESTRATOR-only.
- For the orchestrator the guard is explicitly a guardrail, not a boundary (its own docstring,
  guard.py:19-21, and RISK-003). `find docs/sources -delete` is not seen as touching a protected
  path because the protected fragment is `docs/sources/src-` and the literal `docs/sources` does not
  contain it (guard.py:100-107,153-162), so the orchestrator branch treats it as non-touching. On a
  single workstation, with the orchestrator as the trusted coordinator and pre-commit/commit-msg
  checks plus git history as the backstop, accepting this under RISK-003 is reasonable for Gate 0
  (framework self-tooling, no application code). The risk register entry was updated to name exactly
  these cases (docs/governance/risk-register.yaml:24-45). I concur.
